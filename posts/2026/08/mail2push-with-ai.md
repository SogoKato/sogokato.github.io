メールをスマホの Push 通知に変換する [mail2push](https://push.sogo.dev) というサービスを作って公開しました。実装は全部 Claude Code が書いています。

アプリ: https://push.sogo.dev  
ソースコード: https://github.com/SogoKato/mail2push

サービス自体の紹介は前回の記事 [メールをスマホの通知に変えるサービスを作った](/posts/2026/08/mail2push) に書いたので、今回は開発の進め方について書きます。

## 数字

「AI を使ったら3日でサービスができた」みたいな話にはなりませんでした。仕事をしながらなので、実際はこんな感じです。

* 2026-07-23 〜 08-03の12日間で、41コミット
* ただし実際に手を動かしたのは8日。残りは触っていない

1日あたりのコミット数を並べるとこうなります。

```text
07-23  5     07-28  8
07-24  1     07-29  2
07-25  9     07-31  6
07-26  2     08-03  8
```

土日と、平日の夜に少し。7月27日と30日、8月1〜2日はまったく触れていません。9コミットの日と1コミットの日が隣り合っているのが、細切れで進めていた実態を表していると思います。

できあがったのは、Worker のソースが約2,850行（TypeScript）、マイグレーションが7ファイル、ドキュメントが656行でした。

## 会話で構想を練り、実装へ

会社からの帰り道でチャッピーと会話しながら構想を決めました。最初は「メール→通知」をやってくれる世の中のサービスを調べてもらったのですが、開発前提なら Cloudflare の Email Routing があるよっていうことで、面白そうなので作ってみることにしました。

固まった内容を要約してデザインドックにして、そこからは Claude Code に渡しています。渡したうえで最初に言ったのは、これでした。

> まず調査だけしてほしい。コードは書かないで。

出てきたのが `ARCHITECTURE.md` の1〜8章です。Email Workers の仕様、Workers から Web Push を送る方法、D1 のスキーマ案、Queue を使うべきかどうか、アドレス設計の比較、コスト方針。400行ぐらいの調査レポートが、実装が1行も無い状態で先にできました。

## チェックポイントで区切って進める

`ARCHITECTURE.md`　がいい感じだったので作り始めました。

> この変更をコミットした上で、実装を開始してほしい。最初のチェックポイントはどこになるかな？

以降は「次のチェックポイントまで進めて」の繰り返しです。チェックポイントごとに実機で確認してから次に行きました。

結果として `ARCHITECTURE.md` には、調査レポートの後ろにチェックポイント1〜4が追記されています。

1. Email Worker の実機検証（実際に Cloudflare にデプロイして本物のメールを送る）
2. Web Push 送信の実機検証（iPhone に通知が出るところまで）
3. PWA インストールと通知タップでの起動
4. 公開前のセキュリティ監査

## レビューの手間をどう減らしたか

「AI に書かせるとレビューが大変」はよく言われる話です。今回どうしたかを正直に書くと、コードを読むレビューはしていません。代わりに4つのことをしました。

**動くものを実機で触って判断する。**  
チェックポイントごとに実際に通知を飛ばして、手元の端末で見ました。コードが正しいかではなく、届くかどうかを見ています。

**根拠を説明させる。**  
実装を読む代わりに、なぜそうしたのかを喋らせました。説明が通らないところは、だいたい実装のほうも雑でした。

**観点を投げて、AI 自身にレビューさせる。**  
公開前に4つの観点を渡して、自分で監査させました。認証バイパスみたいなやばめのバグも出てきました。

**レビューさせる前に `/compact` する。**  
12日間ずっと1つのセッションで進めていたので、全体を見直させるときは意図的にコンテキストを圧縮しました。自分が書いたコードを、書いた経緯を覚えたままレビューしても甘くなるんじゃないか、と思ったからです。人間のコードレビューを本人にやらせないのと同じ理屈でした。

ただ、この方法には穴があります。認証をバイパスできてしまうバグは、スマホで動作確認するだけでは分かりません。「セキュリティは十分か」と観点を投げて初めて出ています。つまり、観点を思いつけなかった領域は今も見つかっていないとも言えます。

## 人間が指摘したポイント

実際のやりとりからいくつか紹介します。

### 1. 根拠を問い詰める

「本文サイズに比例して CPU が増えるので、大きいメールは MIME パースをスキップします」という提案が出てきたときのことです。もっともらしく聞こえたのですが、引っかかったので聞きました。

> 素人なので MIME 解析がなにをしてるのかわからないのだけど、説明してくれる？ヘッダー見てるだけならメール本文は関係ないのでは？この処理の必要性は？長い本文のケースでやらなくていいと言い切れるものなの？

この一言で、雑な「スキップします」が「`rawSize` が 256KiB を超えたらヘッダーだけ読んで、本文は `(message too large to preview)` にする」という説明可能な設計に変わりました。閾値の根拠も出てきました（Web Push のペイロード上限が 4KB 程度なので、大きな本文をフルパースする意味が薄い）。

### 2. 「AI くさい」

アプリのアイコンは何度も却下しました。

> ちょっと AI くさい感じがある。アイコンに占めるベルの大きさの割合が小さいのと、ベルの形がイマイチかな。

作り直してきたものにも、まだ言いました。

> モダンで良くなったけど、ちょっと可愛らしさというか、ユニークさがないかな。普通な感じ。人間のデザイナーらしい創意工夫を凝らして。ただし奇をてらわないこと。

最終的にはベルを捨てて、旗の立ったポスト型に落ち着きました。

### 3. 「意味がない」

初期の実装では、通知に件名しか入っていませんでした。

> 初期実装の時に通知に本文が入ってなかったのなんでかな？本文が通知に含まれてないとあまり意味がないと思う。

仕様として間違っているわけではありません。メールが届いたら通知する、という要求は満たしています。でも、件名だけでは内容が十分に分かりません。

### 4. 観点を出すとセキュリティホールが出てくる

公開前に、4つの観点を渡して見直させました。

> * ユーザ体験は十分に考慮されているか。ドキュメントはあるか
> * レートリミット周りは十分か。セキュリティは十分か
> * 利用規約・プライバシーポリシーの同意はあるか
> * 運用は考慮されているか。また、運用時のAIの使い方についてプライバシーポリシーでどう扱っているか

この監査で、認証の完全バイパスが見つかりました。

`POST /login` は、ユーザーが6桁コードを入力するまでブラウザが保持するハンドルとして、マジックリンクのトークンをレスポンスボディにそのまま返していました。ところが `GET /verify?token=` は、そのトークン単体で30日のセッションを発行します。つまりこの2リクエストで、任意のアカウントに入れました。

```sh
curl -X POST /login -d '{"email":"victim@example.com"}'
# -> {"token":"..."}

curl "/verify?token=<返ってきたトークン>"
# -> set-cookie: session=...
```

被害者のメールボックスへのアクセスは不要で、メールアドレスを知っているだけで攻撃できるコードになっていました。

人間が普通に慎重に設計したらこのレベルのミスはしないと思うので、正直びっくりでした。モデルが Sonnet 5 だったか Opus 5 だったか（たぶん Sonnet 5 の high effort くらいだったはず）、コンテキストウィンドウのどのくらいが埋まっていたか、正確に覚えていないですが、まだまだ任せきれないなと感じました。

## ドキュメントがコードの2割あった

Worker 本体が約2,850行なのに対して、`ARCHITECTURE.md` が515行あります。

構成もちょっと変わっていて、1〜8章は実装着手前の技術調査をそのまま凍結してあります。当時「未検証」と書いた箇所も、そのままです。実機で分かったことは末尾にチェックポイント1〜4として追記していく形で、上書きはしません。

この構成に人間は口出ししていません。Claude Code が勝手にこうしました。良い形式なのかどうかは判断がついていなくて、ドキュメントとしては読みにくい部類だと思いますし、515行が分量に見合っているかも分かりません。

ただ、結果的に良かったことが2つありました。

1つは、発見がどの時点で何を覆したかが読めることです。「`web-push` npm は Workers で動かない」「SPF/DKIM の結果は Worker に渡ってこない」といった話が、当初の想定を上書きした記録として残っています。

もう1つは `/compact` との組み合わせです。ずっと1つのセッションで進めていたので、コンテキストは何度か圧縮しています。会話の記憶が薄れても、前提と経緯がファイルに残っているぶんは失われません。前述の「レビュー前にわざと `/compact` する」ができたのも、この土台があったからだと思います。

積み残しも取り消し線付きで残っています。未対応なのは、障害検知が無いこと（Queue が壊れてもユーザーからの報告でしか気づけない）、D1 のバックアップが無いこと、セッションがステートレスな HMAC Cookie なので個別に失効させられないことです。

## 運用での AI 利用をプライバシーポリシーに書いた

`/privacy` の第5条です。

> 運営者は、本サービスの開発・運用・障害調査にあたり、AI コーディングエージェント（Anthropic の Claude Code）を利用しています。障害の原因調査やデータ修正の過程で、この AI エージェントが本番データベースの内容（利用者のメールアドレス、発行したアドレス、保存期間内の通知の記録を含む）を読み取り、また変更することがあります。
>
> これは運営者自身が同じ作業を行う場合と同じ範囲のアクセスであり、目的も運用・障害対応に限られますが、利用者のデータが AI サービスの提供者を経由して処理されうるという点で通常の運用とは異なるため、明記します。

実態としてエージェントに本番 DB を触らせている以上、書かないほうが不誠実だろうと考えました。障害調査でデータを見るのは自分でもやることですが、そこに AI サービスの提供者が挟まるのは、利用者から見れば別の話です。

## 今回のまとめ

* **作ったあとはひたすら「これでいいのか」の判断**
  * 数日で動くサービスはできました
  * そのあとは全体チェックを行い、洗い出した点の対応をする、というのを2セットくらいやりました
  * また、AI は聞かれないと根拠を出さないので「言い切れるものなの？」的な質問を何回もしました
* **浅く広く、確認観点をぶん投げてみる**
  * 「セキュリティは十分か」の一言で認証バイパスが出ました。逆に言えば、聞かなければ出ませんでした
  * 他にも利用規約の整備や UX など、浅くてもいいので幅広く人間がやりたいことを伝えれば、意図を理解して深掘りしてくれます
* **「AI くさい」を指摘できるのは人間だけ**
  * デザインもコピーも、指摘されるまで平均的なものに収束し続けます
