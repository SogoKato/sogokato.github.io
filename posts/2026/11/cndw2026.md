## Agentic AIの本番適用で見えてくる認可の課題とagentgateway

[Agentic AIの本番適用で見えてくる認可の課題とagentgateway](https://event.cloudnativedays.jp/cndw2026/talks/3276)

認可とは何か、なぜ重要か
* 認可には二面性がある
  * 委譲（delegation）: 認可サーバーとクライアントの話。Part 1 で扱う
  * アクセス制御（access control）: ポリシーエンジンとリソースサーバーの話。Part 2 で扱う

Part 1: 委譲（delegation）
* MCP の認可は OAuth 2.1 を使うと仕様で決められている
* AI エージェント × MCP サーバー × スコープの組み合わせごとに同意を求めると、同意疲れが起こる
* そこで認可の拡張として [Enterprise-Managed Authorization](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)（EMA）が規定された
  * 企業向けの拡張で、組織の IdP が一元的に許可する
  * ID-JAG（Identity Assertion JWT Authorization Grant）を使う
* A2A の認可は、MCP よりも実装者に委ねられている部分が大きい
  * 認可の仕様にギャップがあるので注意が必要

Part 2: アクセス制御（access control）
* agentgateway は EMA もサポートしている
* クライアントは ID トークンを agentgateway に渡すだけでよい
  * agentgateway が Enterprise IdP に ID トークンを渡して ID-JAG を取得し、認可サーバーからアクセストークンを受け取る、といったことをやってくれる

> [!NOTE]
> ID-JAG は [IETF OAuth WG のドラフト](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/)です。  
> 流れは2段階で、まずクライアントが SSO の ID トークンを Enterprise IdP でトークン交換して ID-JAG を受け取り、次にその ID-JAG を MCP サーバー側の認可サーバーに出してアクセストークンを受け取ります（RFC 7523 の JWT bearer grant）。IdP はこのときに組織のポリシーを適用します。  
> agentgateway の対応は [Agentgateway now supports ID-JAG and MCP Enterprise Managed Auth](https://aaif.io/blog/agentgateway-now-supports-id-jag-and-mcp-enterprise-managed-auth) で紹介されていて、このトークンのやりとりをクライアントではなくゲートウェイが引き受けるという考え方です。

## LLMを「動かす」から「みんなで使う」へ — Agent Routerで作るマルチテナント推論基盤

[LLMを「動かす」から「みんなで使う」へ — Agent Routerで作るマルチテナント推論基盤](https://event.cloudnativedays.jp/cndw2026/talks/3282)

資料: [LLMを「動かす」から「みんなで使う」へ — Agent Routerで作るマルチテナント推論基盤](https://speakerdeck.com/everpeace/building-multi-tenant-inference-platform-with-agentrouter)

GPU は高いので、モデルを複数のテナントで共有する

要件（一部）

* モデルディスカバリ
* Body based routing
  * Body 内のモデル名でルーティングする
* トークンベースのレートリミット
  * リクエスト数ベースでは意味をなさない
* トークンベースの利用料集計
  * 利用した部門に請求する
* オブザーバビリティ
  * バックエンドに依存せず、ゲートウェイのレイヤーで取りたい
* Advanced routing
  * KV cache aware + load aware なルーティング
  * Disaggregated なルーティング（KV cache を転送する）
  * Gateway API Inference Extension (GAIE)
    * Gateway API の生成 AI 推論向け拡張
    * AI Gateway WG が仕様を策定中

なぜ Agent Router なのか？
* 機能のカバー範囲は、同じく AAIF 傘下の agentgateway とほぼ同じ
* 決め手は
  * データプレーンが Envoy であること（実績と拡張性）
  * Envoy のコミュニティで開発されていること（本家感）
  * 機能がリッチすぎないこと

AAIF に agentgateway や Agent Router があったり、ベンダ系だと Kong AI Gateway, Langfuse AI Gateway[^1] があったりと、最近はゲートウェイのソフトウェアがかなり盛り上がっている印象を受けます。機能が類似していると技術選定に悩みますが、それぞれの特徴や出自を見極めて要件に合うものを選びたいですね。

[^1]: LLM のオブザーバビリティツールとして知られる Langfuse が、2026年11月に [public beta として公開](https://langfuse.com/changelog/2026-11-04-ai-gateway-public-beta)したばかりのゲートウェイです。アプリの接続先（base URL）を差し替えると、すべてのリクエストが Langfuse のトレースとして記録されます。

> [!NOTE]
> Disaggregated は、推論の prefill（プロンプトを読んで KV cache を作る段階）と decode（1トークンずつ生成する段階）を別のサーバーに分ける構成のことです。prefill 側で作った KV cache を decode 側に転送するので、ゲートウェイはそれを踏まえてルーティング先を選ぶ必要があります。

> [!NOTE]
> [Gateway API Inference Extension](https://gateway-api-inference-extension.sigs.k8s.io/) は Kubernetes SIG Network のサブプロジェクトで、Gateway API に InferencePool などのリソースを足し、KV cache の状況や負荷を見て推論サーバーを選ぶ仕組み（Endpoint Picker）を外付けできるようにするものです。これとは別に、2026年3月に [AI Gateway Working Group](https://kubernetes.io/blog/2026/03/09/announcing-ai-gateway-wg/) が発足していて、AI 推論のトラフィックを扱うゲートウェイの機能を提案としてまとめています。

## Kubernetes Schedulingの最前線から見る景色

[Kubernetes Schedulingの最前線から見る景色](https://event.cloudnativedays.jp/cndw2026/talks/3278)

資料: [Kubernetes Schedulingの最前線から見る景色](https://sanposhiho.showcase.cloudnativedays.jp/#p1)

SIG Scheduling の Lead の方のキーノートです。  
全部そろわないなら1つも置かない、というのがギャングスケジューリングです。Pod を作成する時に注目してしまいがちですが、メンテナーの方々がプリエンプションについても考慮されていることなど非常に勉強になりました。

* Pod 単位ではなく、Pod のまとまりとしてスケジューリングするようになってきている
* 例: 4つの GPU を必要とするワークロードがあり、GPU の空きが3つしかない
  * Pod を1つずつスケジュールして3つ埋めてしまうと、リソースを食うだけで何も実行できない
  * → まとまりとして見る必要がある

Topology-aware scheduling
* たくさん通信する Pod どうしは近くに置きたい
* 配置を考える単位が Node から、Node の集まりへ

Preemption
* Pod 単位でプリエンプションすると、Workload を中途半端に壊してしまう
* 追い出しても、より優先度の高い PodGroup を入れられるわけではないなら、どかさない

PodGroup の作成
* PodGroup をユーザーが作らなくてもよくなっている
* Job に指定すると、コントローラーが作ってくれる

CompositePodGroup
* PodGroup をまとめるもの
* LeaderWorkerSet → PodGroup
* 例: CompositePodGroup は zone 単位、PodGroup は rack 単位
* Gang も階層で書ける。3組のうち2組そろえば開始する、など

今後
* v1.38 では主な機能が Beta にそろう見込み

## Runtime Contextから見る脆弱性

[Runtime Contextから見る脆弱性](https://event.cloudnativedays.jp/cndw2026/talks/3174)

ゴール: Runtime Context（実行時の振る舞い）が、脆弱性対応の優先度づけの判断材料になることを理解する

背景
* 脆弱性の数は年々増えている
* NIST は、これまですべての CVE を分析することを目指していたが、今後は優先度をつけると言っている[^2]
* 脆弱性の残留可能性（内部要因）: 自分の環境での影響

Kubescape
* セキュリティプラットフォーム（単一の OSS ではない）
* CNCF の Incubating プロジェクト
* Runtime Context: 実際に動作している環境や、その実行時の振る舞いに関する情報

PostgreSQL 18.6 のイメージを pull して試した例
* イメージスキャンの結果は13件 → Runtime Context で絞ると、関連する脆弱性は5件
* 先日話題になった brotli の CVE-2026-111497 は、使っていないのでフィルタアウトされていた

ContainerProfile
* CRD で、eBPF などを使ってコンテナの動作を観測する
* コンテナの作成を検知した後、観測結果を一定間隔でマージし、ContainerProfile として保存する
* デフォルトで24時間学習する
* 実行したコマンド、アクセスしたファイル、syscall などを記録する

Kubevuln
* 脆弱性の診断をするコンポーネント
* 結果は次のカスタムリソースに入る
  * SBOMSyft: ライブラリと、そのライブラリに含まれるファイル
  * SBOMSyftFiltered: 実際に観測された構成要素
  * VulnerabilityManifest: 観測された脆弱性

注意: 「関連性がない」は「悪用されない」ではない
* 次の3つはそれぞれ別の状態で、優先度を判断するための材料になる
  1. 存在する
  2. 関連性がある
  3. 悪用可能である

Runtime Context を使った異常検知
* Mandiant の M-Trends 2026 でも、正常なシステムとの比較や外れ値の分析が挙げられている
  * ↑ Kubescape の観測結果が使える！
* Rules と RuntimeRuleAlertBinding というカスタムリソースを使う
* Rule の適合状況は、Node Agent が /metrics として公開する

この秋は脆弱性対応にばかり追われていたというエンジニアは多いと思います。診断ツールをかけるとたくさんの脆弱性が出てきたりしますが、その際に自分たちの環境のエビデンスに基づいた判断ができるというのは非常に説明しやすいものでしょう。明日から試してみたくなりました。

[^2]: 2026年4月に [NVD の運用変更として発表されたもの](https://www.nist.gov/node/1910421)です。4月15日からは、CISA の KEV カタログに載ったものや、連邦政府が使うソフトウェアなどの CVE を優先して分析し、それ以外は登録はするものの詳細な分析（CVSS スコアや影響製品の付与）は優先度を下げるとしています。

## システムプロンプト依存からの脱却: AIエージェントを守る意図ベースの認可とは

[システムプロンプト依存からの脱却: AIエージェントを守る意図ベースの認可とは](https://event.cloudnativedays.jp/cndw2026/talks/3290)

資料: [システムプロンプト依存からの脱却: AIエージェントを守る意図ベースの認可とは](https://www.docswell.com/s/Neri78/ZN76PR-fga-intent-based-authorization)

* エージェントは「答える」から「動く」へ
* 「権限がある」と「意図どおり」は別物

例: 会議を設定するエージェント
* カレンダーのメモに書かれた悪意のあるプロンプトを読み込んで、意図しない動きをするかもしれない
* エージェントとしては権限の範囲内で、悪いことはしていない
* しかしユーザーの意図としては、会議の設定だけをしてほしかった

エージェントが持つすべての権限 > 今のタスクに必要な権限
* ユーザーの意図を認可に落とし込むには？
* → とても難しかった。銀の弾丸はないと前置きしつつ、アイデアを共有する

タスク単位で、ユーザーの意図に沿った権限を設定する
* user「会議を設定してほしい」→ agent:scheduler、task:T → tool:calendar_create_event

RBAC や ABAC で実現できるか
* RBAC: ロールが静的なので、タスクという一時的なライフタイムを表そうとすると動的なロールが爆発する
* ABAC: できそうではあるが、ユーザ→タスク→エージェント→ツールといった走査をアプリがやらないといけない

そこで ReBAC の出番
* 関係性によって動的に決まるアクセス制御
* OpenFGA については過去にもセッションをしている

流れ
* Pre-planning: 計画用の LLM が必要なツールを選び、システム上でタプルを作成・登録する
  * ユーザーの指示だけを見て決める
* 実行: 外部からの入力を含む
* 実行後は認可情報を消す（タプルを消す）

FGA のモデル
* tool:X の can_call
  * 条件1: task の can_execute（＝ task の assignee であること）
  * AND 条件2: available_to（＝ 利用可能ツール一覧に登録済み）

実行ゲートウェイでの Check
* agent が tool の can_call を持つか
* 呼び出し元の user が task の initiator か
* どちらかが false なら実行しない（Fail Closed）

課題と限界
* Check の範囲の混同
  * → エージェントのインスタンスをタスクの中に作ることで軽減
* 実行中の新たな要求（「やっぱり Slack にも送って」）
  * → アプリケーションとして明示的に同意をとる

さらなる課題
* 意図の定義の揺らぎ
  * 「MTG を設定して」の1文に、どこまでの意図を含むのか？
* リソースの名前解決（自然言語 → 実際のシステムの ID）
* Pre-planning へのインジェクション
  * ユーザーの入力そのものが信頼できない場合は、この仕組みでは難しい
* 許可されたツールの悪用
  * 「メールで送信して」（何を？）
  * → 多段の防御が必要

AI エージェントの認可や ReBAC は、遅まきながら最近私もよく考えている分野です。人間ではなく AI エージェントとしてのアイデンティティの話は聞いたことがありますが、今回のようにタスク単位で ReBAC のタプルを作るというアイデアは新鮮でした。その分まだ課題がたくさんあることは登壇者の方が検討されている通りですが、OWASP Agentic Top 10 対策などを突き詰めていくと自然とそこに辿り着きそうな気がします。

## SBOM生成ツールで2026 Minimum Elementsはどこまで満たせるのか

[SBOM生成ツールで2026 Minimum Elementsはどこまで満たせるのか](https://event.cloudnativedays.jp/cndw2026/talks/3182)

* CISA の「2026 Minimum Elements for a Software Bill of Materials」という、SBOM の最小要素を定めたドキュメントの紹介
* SBOM 生成ツールで作った SBOM に足りない項目の補い方

anchore/syft でコンテナイメージから SBOM を作ってみる
* これでよいのか？
* 読み取れない情報がある
  * この SBOM を作ったのは誰？
  * ビルド前に作ったのか、ビルド後に作ったのか？
* 満たすべき最低限の期待値を定めたのが Minimum Elements

データフィールド
* SBOM メタデータ: SBOM 自体に関する情報
  * 署名を含む（具体的な署名方法の指定はない）
  * 作成者が埋められる項目
* SBOM コンポーネントデータ: SBOM に記載するコンポーネントの情報
  * 作成者にも分からないものがある → 不明であること（UNKNOWN）を明示する
  * ただし UNKNOWN の書き方のルールはなく、今後議論が進むかもしれない

カバレッジ
* どの深さまで載せるかの具体的な基準はなく、指針が書かれているだけ
* EU の CRA やドイツの BSI などのプラクティスを参考に決める

不明な情報の明示
* CycloneDX で不明であることを明示できるのは、依存関係に関する一部のフィールドだけ

結論: 自動生成できそうなことと、できないことがある
